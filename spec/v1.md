# Bridge ABI v1

Bridge ABI v1 defines a host-neutral interface for formatting source code with a WebAssembly guest.

This specification covers formatter endpoints, whole-file and range formatting
requests, reusable formatter configuration, and optional synchronous embedded
formatting through the host. Formatter metadata is outside v1.

## Conventions

- WebAssembly pointers and lengths are `u32`.
- All integers stored in memory use little-endian byte order.
- Formatter configuration is opaque bytes. Its encoding belongs to the formatter adapter and guest implementation.
- Config ids are nonzero `u32` values. A host must not reuse an id while its
  registered configuration is still live.
- Hosts must encode `source` and `filename` as UTF-8 without replacement.
  Host-language strings that cannot be represented losslessly as UTF-8 are
  rejected before invoking the guest.

## Instance and call ownership

A v1 guest has either zero imports or the optional embedded-formatting import
group and exports one unshared wasm32 memory named `memory`. Shared memory,
threads, asynchronous calls, and reentrant calls into the same instance are
outside v1. Initialization, if required by the guest
language, completes once before the first Bridge operation.

One host owner manages an instance for its entire lifetime. Calls are serial.
After attaching a runtime, application code must not independently call guest
exports or create another runtime for the same instance. Multiple formatters
or concurrent work use separate instances.

Each input transaction follows this sequence:

1. Call `wasm_fmt_alloc(len)` exactly once and write the complete input.
2. Invoke one formatter endpoint or `wasm_fmt_register_config` with exactly
   that pointer and length. A zero-length allocation returns pointer `0`.
3. Read and validate the response before invoking any other mutating operation.
4. Call `wasm_fmt_reset()` after a normal response, including status `3`.

Only the current input allocation is valid. Another allocation or reset
invalidates its contents. Invoking an input operation consumes the allocation;
the host must not reuse it for another operation. Pointers into arbitrary
memory or subranges are not valid inputs. The guest may trap on a violation of these host preconditions.
Formatters and decoders must not retain borrowed request data after returning.

`reset` invalidates transient input, output, and error data; it may retain
buffer capacity. It neither releases registered configurations nor promises to
shrink WebAssembly linear memory. Config release is a standalone serial
operation and requires no input allocation.

A trap or malformed ABI response permanently invalidates the instance. The
host must make no further guest calls, including reset, and must discard all
its config handles. A new instance is required. Host input errors detected
before entering the guest and valid status `3` responses do not invalidate it.

## Exports

A v1 guest exports the following shared functions:

```text
wasm_fmt_abi_version() -> u32
wasm_fmt_alloc(len: u32) -> u32
wasm_fmt_reset() -> void

wasm_fmt_register_config(id: u32, ptr: u32, len: u32) -> u32
wasm_fmt_release_config(id: u32) -> void

wasm_fmt_output() -> u32
wasm_fmt_error() -> u32
```

It also exports one or more formatter endpoints:

```text
wasm_fmt_<endpoint>(req_ptr: u32, req_len: u32) -> u32
```

`wasm_fmt_format` is the default formatter endpoint.
`wasm_fmt_format_range`, when present, is the conventional specialized endpoint
for requests containing the `ranges` field. All formatter endpoints use the
same request, status, output, and error formats.

The `<endpoint>` suffix is an ASCII identifier matching
`[A-Za-z_][A-Za-z0-9_]*`. The shared export suffixes `abi_version`, `alloc`,
`reset`, `register_config`, `release_config`, `output`, and `error` are
reserved and cannot name formatter endpoints.

`wasm_fmt_abi_version()` returns `1`.

`wasm_fmt_reset()` invalidates transient input, output, and error buffers. It does not release registered configurations.

## Status codes

```text
0 none / unchanged
1 full update
2 partial update
3 error
```

A formatter endpoint may return `0`, `1`, `2`, or `3`.

- `0`: the formatter explicitly reports `Unchanged`; the host returns the original source.
- `1`: the host reads a full UTF-8 replacement from `wasm_fmt_output()`.
- `2`: the host reads a partial-update edit sequence from `wasm_fmt_output()` and applies it to the source.
- `3`: the host reads a UTF-8 error message from `wasm_fmt_error()`.

`wasm_fmt_register_config` returns `1` or `3`. On `3`, the host reads `wasm_fmt_error()`.

Unknown status codes are ABI errors.

## ByteString

Output and error functions return a pointer to:

```text
u32 byte_length
u8[byte_length] payload
```

The payload begins at `ptr + 4`. A returned pointer is valid until the next operation that mutates transient state or until `wasm_fmt_reset()`.

The payload format depends on the operation and status. Full output from format status `1` and errors from status `3` are UTF-8. Partial updates from format status `2` use the binary format below.

Guests must not truncate a payload length to fit `u32`. If a result and its
four-byte prefix cannot be represented by both `u32` and the guest's address
space, a guest FDK reports status `3` with a bounded fallback error.

## Partial update

Partial update is an alternate result representation available to every
formatter endpoint. It is independent of whether a request contains ranges and
does not imply range formatting.

For format status `2`, `wasm_fmt_output()` returns an outer `ByteString` whose payload is:

```text
u32 update_count

repeated update_count times:
  u32 start
  u32 end
  u32 text_byte_length
  u8[text_byte_length] text
```

`start` and `end` are byte offsets into the UTF-8 bytes of the request's `source` field. Each edit replaces the half-open range `[start, end)` with `text`, which must itself be valid UTF-8.

The complete edit sequence must satisfy all of these rules:

- The payload contains the declared `update_count` exactly. Truncated counts, edit headers, or replacement text are errors.
- No bytes follow the final declared edit.
- Each range satisfies `start <= end <= source_byte_length`.
- Both `start` and `end` fall on UTF-8 character boundaries in the source.
- Edits are in ascending, non-overlapping order. For every edit after the first, `start` is greater than or equal to the previous edit's `end`.
- Multiple empty insertions with the same `start == end` are valid and are applied in wire order.
- An `update_count` of zero is valid and produces the original source while preserving format status `2`.

The host validates the entire payload and every edit before constructing output. It then applies the edits atomically to the source's UTF-8 bytes and decodes the final bytes as a string. A malformed partial update is an ABI error; the host must not return a partially applied result.

Guest FDKs also validate formatter-provided edits before returning status `2`.
If the formatter returns an invalid range, ordering, overlap, or payload size,
the FDK returns status `3` and exposes the structural error through
`wasm_fmt_error()`. Hosts still validate status `2` payloads because a Wasm
guest is not assumed to be trustworthy.

## Format request

A formatter endpoint receives one request containing an eight-byte magic
followed by TLV fields:

```text
u8[8] magic  // ASCII "WASM-FMT"

repeated until offset == req_len:
  u16 tag
  u16 field_flags
  u32 byte_length
  u8[byte_length] payload
```

There is no field count or request-local version. `req_len` marks the end, and the ABI version defines the request format.

### Field flags

```text
bit 0      critical
bits 1..15 reserved; must be zero
```

An unknown non-critical field is skipped. An unknown critical field is an error.

### Core tags

| Tag | Name | Payload | Rules |
| ---: | --- | --- | --- |
| 1 | `source` | UTF-8 source bytes | Required exactly once; an empty payload is valid. |
| 2 | `filename` | UTF-8 filename/path | Optional and unique. Missing and present-empty are distinct. |
| 3 | `inline_config` | Opaque formatter bytes | Optional and unique. |
| 4 | `registered_config` | Little-endian `u32` config id | Optional, unique, and exactly four bytes. |
| 5 | `ranges` | Range sequence described below | Optional, unique, and uses flags `0`. Missing and present-empty are distinct. |

`inline_config` and `registered_config` are mutually exclusive.

When neither config field is present, configuration is absent. A guest-language
FDK may map that absence to a default value or preserve it as an optional
value. The ABI does not represent a default as serialized bytes and does not
treat absence as an empty config payload. An endpoint that does not support
configuration rejects requests containing configuration. Registration validates
the guest's single configuration schema independently of endpoint selection;
a guest without configuration support rejects registration.

Known fields with unsupported flag bits, duplicate core fields, truncated headers, truncated payloads, missing source, invalid registered ids, and trailing malformed bytes are errors.

### Ranges

The `ranges` payload is:

```text
u32 range_count

repeated range_count times:
  u32 start
  u32 end
```

Each range is a half-open `[start, end)` byte range in the UTF-8 bytes of the
request's `source` field. The complete payload must satisfy all of these rules:

- The payload contains exactly `4 + range_count * 8` bytes.
- Each range satisfies `start <= end <= source_byte_length`.
- Both `start` and `end` fall on UTF-8 character boundaries in the source.
- An empty range list is valid.
- Range order is significant and preserved.
- Ranges may be out of source order, overlap, repeat, or be empty.

The absence of tag `5` means a whole-file request. A present tag `5` with
`range_count == 0` is an explicit empty range request; guests and hosts must not
conflate those states.

The JavaScript host runtime invokes `wasm_fmt_format_range` for a range request
when that endpoint is exported. Otherwise it invokes `wasm_fmt_format` with the
same request. A default endpoint that does not accept ranges reports status
`3`; the fallback does not permit silently treating a range request as a
whole-file request.

## Registered configuration lifecycle

All configuration-aware endpoints in one guest must share one formatter
configuration schema and encoding. An endpoint may omit configuration support,
in which case it rejects requests containing a config field.

The host chooses a nonzero config id and calls `wasm_fmt_register_config` with
formatter-owned encoded bytes. The guest must decode and validate the
configuration eagerly. Success returns status `1`; invalid configuration
returns status `3` without creating a registration. Successful `createConfig`
therefore guarantees semantic configuration validation.

Registering an already-live id returns status `3` and preserves the existing
configuration. A released id may be reused by an ABI host; the JavaScript
runtime allocates monotonically increasing ids and reports exhaustion instead
of wrapping. Registered configuration is logically read-only during formatting;
formatter code must not mutate it, including through reference-valued fields.
Rust endpoints borrow the stored configuration for the duration of the call.
Go configuration values must obey this read-only contract even when they
contain slices, maps, or pointers.

A format request refers to it with tag `4`. The host calls `wasm_fmt_release_config(id)` when the handle is no longer needed. Releasing an unknown id is a no-op.

Configuration handles exposed by a host SDK are host-language concepts; only the numeric config id crosses the ABI.

## Traps

Status `3` represents an error returned normally through the ABI. A WebAssembly
trap has no status code or readable error `ByteString`; the host reports it as
an invocation failure. Guest FDKs are not required to recover language panics,
unwinds, or process-level allocation failures as formatter errors.

After a trap the instance must be discarded, as specified by the ownership contract above.

## Synchronous embedded formatting

A guest may import the following complete function group from `wasm_fmt_host`.
All other imports remain forbidden. Import-free guests remain valid v1 guests.
Types below are Wasm `i32` interpreted as unsigned `u32`.

```text
format_embedded(req_ptr: u32, req_len: u32) -> u32
embedded_result_len() -> u32
read_embedded_result(dst_ptr: u32, dst_len: u32) -> void
```

These imports are callable only while a formatter endpoint is executing. They
are not available during module start, initialization, allocation, registration,
output/error retrieval, or reset. Supported FDKs give the formatter body a
call-scoped Host capability after decoding its input/config; decoders receive
no such capability. Hosts enforce the outer operation phase, but cannot infer
an arbitrary guest's internal decoder execution from the wire.

A synchronous host callback may invoke a different idle formatter instance.
It must not reenter any active instance, including indirect cycles. The calling
instance remains busy throughout the callback. The host must not call any of
its exports to allocate or deliver the callback response. No async suspension,
shared memory, global formatter registry, or resource-loading operation is part
of this protocol.

### Embedded request

The request begins with the eight ASCII bytes `WASM-EMB`, followed by TLV fields
using the same little-endian headers and critical/reserved flags as format
requests, but a separate tag namespace:

| Tag | Field | Payload | Rules |
| ---: | --- | --- | --- |
| 1 | source | UTF-8 | Required, unique; empty is valid |
| 2 | filename | UTF-8 | Required, unique, nonempty |
| 3 | line_width | u32 LE | Optional, unique, exactly four bytes, positive |

FDKs emit source and filename as critical and line_width as noncritical.
Unknown noncritical fields are skipped; unknown critical fields, unsupported
flags, duplicates, invalid UTF-8, malformed lengths, or missing required fields
are protocol errors. `req_len` includes the magic and every field.

`filename` is a virtual filename such as `embedded.py` or `embedded.tsx`, for
selecting a formatter and syntax mode. It does not grant filesystem access or
claim the identity of the containing document. The embedding formatter maps
language tags to filenames. `source` is the prepared fragment, which need not
be a verbatim slice of the outer source. No outer-document offsets are implied.
`line_width` is a formatting hint: the host maps it into the target formatter's
configuration if supported. Target configuration remains host-owned; registered
config ids never cross between instances. Full fragment formatting is requested;
there are no embedded request ranges or generic JSON config overrides in v1.

### Response and transfer

`format_embedded` returns status `0` (no replacement), `1` (replacement text), or
`3` (error text). Status `2` and all other values are invalid. No replacement
includes a host with no handler or no matching formatter. An empty replacement
is distinct from no replacement. Hosts do not have to compare text to infer
no change. A successful replacement or error produces one host-owned pending
UTF-8 payload, without a ByteString length prefix.

The guest queries its byte length with `embedded_result_len`, allocates an
independent writable buffer, and calls `read_embedded_result` with exactly that
length. The copy consumes the payload. Length queries do not consume it. For an
empty payload the copy still occurs, with pointer and length both zero. Partial
copies are not supported. The host obtains a fresh view of guest memory at copy
time because the guest's allocation may have grown memory.

The request buffer is guest-owned and read-only during the first import. The
host validates and decodes it into host-owned data before calling application
code; it retains no guest memory views across application callbacks. The guest
FDK's response buffer must not alias its live input, config, or formatter state.
It copies/owns the response before returning to formatter code. The FDK must not
reuse the top-level alloc slot or acquire an instance-state lock already held
by the outer format invocation.

Each instance has at most one pending result. A second request before consuming
it, result access without a pending result, imports during host callback
execution, an invalid destination, or returning from the endpoint with an
unconsumed result is a protocol violation. Hosts retire that instance even if
application code catches the import's exception. Pending buffers and callback
references are released on every endpoint exit, including traps.

### Errors and embedding policy

Normal callback failures become status `3`; invalid synchronous return types
and promises are callback errors. Error reporting must tolerate arbitrary
thrown values without accidentally throwing across Wasm. A host may substitute
a bounded fallback error when an error cannot safely be represented. Import
protocol violations instead trap/fail the invoking instance.

A child formatter trap retires the child. It can be reported as a normal
embedded error to the parent; the parent remains usable if it completes with a
valid ABI response. An uncaught trap crossing the parent retires it too.

How a formatter treats a normal embedded error is an embedding policy. The
wasm-fmt Markdown adapter uses strict propagation: unavailable languages are
skipped; callback failures fail the whole document. It remembers the first
callback error even when its underlying library swallows it, skips further
callbacks in that call, and returns the error instead of a partial document.
Skipping a fragment still allows the Markdown formatter to change surrounding
fence layout and indentation.

This transfer model is informed by dprint's synchronous host-format protocol.
Bridge uses its own TLV schema, existing error status `3`, explicit no-replacement
result, and per-instance ownership; it is not wire-compatible with dprint.
